# 다음으로 — 실시간 수업 소통창 PRD
## 제품 요구사항 및 개발·검수 기준 v1.5

- 작성일: 2026-10-28 (한국 시간)
- 문서 목적: PO·PM, 디자이너, 개발자, 테스트 참여자가 동일한 제품을 이해하고 구현·검수하기 위한 기준.
- 제품명: ‘다음으로’는 가칭. 명칭은 기능 구현에 영향을 주지 않는다.
- 상태: 구현 착수용 제안 기준안. 사용자와 합의한 방향은 확정 요구로, 이 문서가 추가로 정한 수치·정책은 초기 기본값으로 구분한다.
- 산출물: 데스크톱 웹 서비스. 이 문서는 서비스 구현물이나 검증 결과가 아니다.
- 핵심 기술 가정: Windows 11 + 데스크톱 Chrome + HTTPS + Document Picture-in-Picture(PiP).
- 중요한 한계: PRD만으로 오류가 전혀 없는 구현을 보장할 수 없다. 불확실한 환경은 착수 전 기술 검증과 인수 테스트로 확인한다. 확인되지 않은 동작을 지원한다고 표시하지 않는다.

## 0. 한눈에 이해하기

### 0.1 서비스 한 문장

젭에서 수업을 듣고 VS Code 등으로 실습하는 수강생이, 작업 화면 위의 작은 창에서 상태를 한 번의 클릭으로 전달하고 익명 질문을 남기는 수업 소통 도구.

### 0.2 해결하려는 상황

강사: “실습 준비됐나요?”, “이해했나요?”, “다음으로 넘어갈까요?”

수강생은 채팅창을 찾아 이동하고 글을 입력하는 대신, 화면 위에 떠 있는 작은 창에서 응답한다. 강사는 작은 진행창에서 긍정·대기·미응답을 구분해 확인한다. 수업 중 생긴 질문은 익명으로 남기고, 다른 수강생은 ‘저도 궁금해요’를 표시한다. 강사는 쉬는 시간이나 수업이 끝난 뒤 미답변 질문을 확인한다.

### 0.3 제품의 세 가지 기능

| 기능 | 수강생이 하는 일 | 강사가 보는 것 |
|---|---|---|
| 상태 응답 | 현재 요청에 응답·응답 변경 | 응답별 인원, 미응답, 연결 상태 참고 |
| 익명 질문 | 200자 이내 질문 작성 | 미답변 질문 목록 |
| 질문 공감 | 🙋 저도 궁금해요 선택·취소 | 질문별 공감 수 |

### 0.4 만들지 않는 것

채팅 대체 플랫폼, 화상 수업, 젭 플러그인, 출결·성적 관리, LMS, AI 답변, 학습능력 평가, 수업 녹화, 자동 음성 인식, 전체 화면 감시, 학생별 이해도 순위.

### 0.5 구현에서 절대 바꾸지 않을 핵심

1. 실제 다른 컴퓨터의 참여자 사이에 응답이 전달되어야 한다.
2. 일반 팝업만 만든 뒤 ‘항상 위에 표시’가 구현됐다고 간주하지 않는다.
3. 무응답은 긍정도 부정도 아니다.
4. 새 요청은 이전 요청과 별개의 응답 회차다.
5. 전송 확인 전에는 완료로 표시하지 않는다.
6. 익명 질문 작성자의 식별 정보를 다른 참여자의 응답 데이터에 포함하지 않는다.
7. 서버가 권한·집계·최종 상태를 결정한다.
8. 작은 창은 작업 중인 앱의 포커스를 자동으로 빼앗지 않는다.

## 1. 요구사항의 확정 수준

| 구분 | 내용 | 처리 |
|---|---|---|
| 사용자 합의 | 작은 창, 다른 작업 화면 위 표시, 상태 응답, 익명 질문, 공감, 강사의 질문 확인 | P0 필수 |
| 문서 기본값 | 30명 정원, 200자, 보관 24시간, 수치 목표, 질문 정렬, 기술 스택 | 구현 기준으로 적용하되 변경 시 문서 수정 |
| 사전 검증 필요 | 실제 젭·VS Code 환경에서 PiP 유지, 화면 공유·전체 화면, 백그라운드 연결 안정성 | 기술 검증 통과 후 지원 범위 확정 |
| 과제 운영 확인 | 1차 과제에서 Supabase·익명 세션·DB 사용 허용 여부 | 멘토 확인. 금지 시 범위를 재합의 |
| 가설 | 채팅보다 응답이 빠르고 미답변 질문을 찾기 쉽다 | 사용자 테스트로 확인 |

문서의 수치와 테스트 목표는 실측 결과가 아니다. “사용자가 실제로 불편해했다”는 표현은 인터뷰 근거가 확보된 뒤 발표에 사용한다.

### 1.1 변경 원칙

기능·상태·API 계약·집계 분모·보관 정책 변경 시 버전을 올린다. 변경 이유, 영향받는 요구사항 ID, 수정할 테스트를 기록한다. 개발자가 지원 환경이나 익명 범위를 조용히 바꾸어서는 안 된다.

## 2. 사용자와 문제 정의

### 2.1 주요 사용자

| 사용자 | 상황 | 목표 | 주된 불편 가설 |
|---|---|---|---|
| 수강생 | 젭, VS Code, 브라우저 자료를 동시에 사용 | 실습을 이어가면서 간단하게 의사 전달 | 채팅 탐색·입력·복귀에 주의가 분산됨 |
| 강사 | 강의 자료나 실습 화면을 공유 | 다음 단계 진행 여부 파악 | 침묵이 준비 완료인지 미응답인지 불명확 |
| 강사 | 쉬는 시간·수업 종료 직후 | 남은 질문 처리 | 질문이 다른 채팅 사이에 섞이고 중복됨 |

### 2.2 실제 확인할 인터뷰

- 최근 수업에서 “이해했나요?”에 어떻게 응답했는가?
- 응답하지 않았다면 무엇 때문인가? 창 이동, 타이핑, 눈치, 질문을 못 들음 중 어느 것인가?
- 현재 채팅 이모지만으로 충분하지 않은 구체적인 순간은 무엇인가?
- 강사는 현재 미응답과 준비 완료를 어떻게 구분하는가?
- 익명 질문 창이 추가되면 강사는 언제 확인할 수 있는가?
- 작은 창이 실습 내용을 가리면 어디로 옮기고 싶은가?

### 2.3 차별화의 범위

‘저도 궁금해요’ 자체는 기존 채팅에도 있다. 본 제품의 가치는 별도 소통 채널의 신기함이 아니라, 실습 화면 위 접근성과 상태 요청·미응답 구분·미답변 질문 처리를 하나의 작은 흐름으로 제공하는 데 있다. 강사가 사용하지 않으면 추가 질문 창구만 생기므로 양측 사용을 전제로 한다.

## 3. 목표·비목표·성공 기준

### 3.1 제품 목표

- 수강생이 실습 화면을 탐색해 채팅창을 찾지 않고 상태 응답.
- 강사가 참여자의 응답 현황을 읽고 직접 진행 여부 판단.
- 수업 흐름을 끊지 않는 익명 질문 수집.
- 기술 실패를 숨기지 않고 재시도·복구 경로 제공.

### 3.2 검증 목표 — 모두 목표치이며 아직 미측정

| 지표 | 정의 | 초기 합격 목표 |
|---|---|---|
| 상태 응답 시간 | 요청이 수강생 화면에 표시된 시점부터 서버 응답 승인까지 | 채팅 조건 대비 참가자별 중앙값 감소율의 중앙값 30% 이상 |
| 15초 내 응답률 | 제시 후 15초 안에 승인된 응답 / 테스트에서 제시한 전체 요청 | 90% 이상 |
| 미답변 식별 정확도 | 정확히 찾은 미답변 질문 / 찾아야 할 미답변 질문 | 90% 이상 |
| 원격 반영 지연 | 서버 승인 이후 다른 클라이언트에 반영되기까지 | 정상 테스트 네트워크에서 P95 2초 이하 |
| PiP 유지 | 지원 환경에서 앱 전환 후 보임·클릭 가능 | 필수 시나리오 전부 통과 |
| 데이터 정합성 | 중복·변경·재연결 후 서버 기준과 표시 일치 | 필수 테스트에서 오류 0건 |

30명 모의 접속은 기능·부하 확인이며 실제 30명의 사용자 테스트로 표현하지 않는다.

### 3.3 범위 우선순위

| 등급 | 기능 |
|---|---|
| P0 | 방 생성·참여, 역할 권한, PiP, 세 가지 요청, 실시간 집계, 익명 질문, 공감, 답변 완료, 재연결, 오류 표시, 정합성·권한 테스트 |
| P1 | 최신순·공감순 전환, 강사의 부적절 질문 숨김, 기본 접근성, 검증용 이벤트 기록 |
| 제외 | AI, 답글, 대댓글, 파일·이미지, 자동 질문 병합, 다운로드 리포트, 장기 수업 이력, 강사 공동 관리, 앱 설치·확장프로그램 |

이 문서에서 P1도 최종 계획에 포함한다. 일정이 부족하면 최신순만 남기는 등의 축소를 변경 기록에 명시한다. PiP·실제 통신·권한 검증을 생략하고 완성으로 보고하지 않는다.

## 4. 지원 환경과 기술 검증 게이트

### 4.1 첫 버전의 지원 선언

- 필수 검증 OS: Windows 11. 실제 테스트 빌드 번호 기록.
- 필수 브라우저: 테스트 시점 Chrome 안정 버전. 정확한 버전 기록.
- 네트워크: 인터넷 연결, HTTPS 배포 환경. 로컬 개발 예외는 localhost.
- 수업 환경: 젭을 사용하는 Chrome 창, VS Code 일반 창, 자료용 Chrome 창.
- 화면: 1366×768 및 1920×1080, OS 배율 100%·125%에서 확인.
- Mac, Edge, Firefox, Safari, 모바일: v1 정식 검증 대상 아님. API 존재 여부로 탐지하되 미검증 지원을 보장하지 않음.
- OS 보안 화면, 잠금 화면, 독점 전체 화면, 다른 가상 데스크톱, 다른 PiP와의 동시 유지: 보장 대상 아님.

### 4.2 ‘항상 위’의 정확한 의미

수강생이 일반 창 상태의 젭·VS Code·브라우저로 작업을 전환했을 때 PiP가 보이고 클릭 가능한 것. OS 전체를 지배하는 오버레이나 모든 전체 화면 위 표시를 의미하지 않는다. 최대화·브라우저 F11·젭 자체 전체 화면은 각각 따로 시험하고 결과를 지원 환경 표에 남긴다.

### 4.3 GATE-01: 실제 제품 개발 전 검증

최소 화면에 버튼 두 개와 카운터만 구현해 다음을 시험한다.

| 번호 | 시험 | 합격 기준 |
|---|---|---|
| G1 | 작은 창 띄우기 버튼 클릭 | 사용자 제스처로 PiP 열림 |
| G2 | VS Code에서 코드 입력 | PiP 유지, 입력 포커스는 VS Code |
| G3 | 젭 창·자료 창·VS Code를 각 10회 왕복 | PiP가 묻히거나 닫히지 않음 |
| G4 | 최대화·F11·젭 전체 화면 각각 사용 | 결과와 제한을 개별 기록 |
| G5 | 젭 화면 공유 | 공유된 내용과 로컬 PiP 동작을 두 번째 기기에서 확인 |
| G6 | 원래 서비스 탭을 뒤에 두고 10분 실습 | 요청 수신·응답 전송 유지 |
| G7 | PiP 닫기·원래 탭 새로고침 | 복구 안내, 임의 자동 재개 금지 |
| G8 | 인터넷 10초 끊기 후 복구 | 실패 표시 후 서버 상태 재동기화 |

G2·G3·G6 실패 시 핵심 가치 미충족이다. 일반 팝업으로 바꾸고 통과로 처리하지 않는다. 지원 범위를 좁히거나 별도 데스크톱 앱을 차기 범위로 검토하고, PRD를 수정한다.

### 4.4 배포 조건

프로그램은 iframe 내부 임베드가 아니라 별도 최상위 HTTPS 페이지로 사용한다. 젭 내부 삽입이나 젭 계정 연결은 요구하지 않는다. 통과한 환경만 시작 화면에 안내한다.

## 5. 주요 용어

| 용어 | 정의 |
|---|---|
| 방(room) | 한 번의 수업을 위한 데이터·권한 단위 |
| 강사(host) | 방을 만든 세션. 방당 한 명 |
| 수강생(student) | 참여 코드로 방에 들어온 익명 인증 세션 |
| 요청(round) | 준비·이해·진행 확인 중 한 번 발송한 질문 |
| 긍정(yes) | 요청의 첫 번째 선택지 |
| 대기(no) | 요청의 두 번째 선택지. 실패·오답을 의미하지 않음 |
| 미응답 | 해당 요청 대상자 중 서버에 저장된 선택이 없는 사람 |
| 질문(question) | 수강생이 익명으로 남긴 짧은 텍스트 |
| 공감 | 질문당 한 세션이 남기는 ‘저도 궁금해요’ 선택 |
| 답변 완료 | 강사가 설명했다는 표시. 모든 수강생의 이해 완료와 다름 |
| 연결 확인 | 최근 heartbeat가 서버에서 확인된 상태. 집중·출석의 증거 아님 |
| 초기 기본값 | 이 문서가 구현 일관성을 위해 정한 값. 실측·사용자 확정과 구별 |

## 6. 전체 사용자 흐름

### 6.1 강사

시작 → 파일럿 생성 코드 입력 → 수업명 입력 → 방 생성 → 참여 링크 공유 → 작은 창 열기 → 요청 보내기 → 집계 확인 → 요청 종료 → 질문 탭 확인 → 구두 설명 → 답변 완료 → 수업 방 종료.

### 6.2 수강생

참여 링크 또는 코드 → 익명 참여 세션 생성 → 개인정보 안내 확인 → 작은 창 열기 → 요청 수신 → 응답 → 필요 시 변경 → 익명 질문 등록 또는 기존 질문 공감 → 수업 종료 화면 확인.

### 6.3 수업 종료와 서비스 방 종료의 구별

강사가 말로 수업을 끝내거나 젭에서 퇴장해도 본 서비스 방은 자동 종료되지 않는다. 종료 직후 질문을 확인할 수 있도록 서비스의 ‘방 종료’를 별도로 제공한다. ‘방 종료’ 후에는 질문·공감·응답·답변 상태 변경 모두 불가능하고 읽기만 가능하다.

## 7. 방·역할·참여 정책

### ROOM-01 방 생성

- 수업명: trim 후 Unicode code point 기준 1~30자.
- 강사 한 세션은 열린 방을 동시에 1개만 소유한다. 기존 방이 있으면 복귀 링크 표시.
- 코드: 서버에서 암호학적으로 생성한 8자리 대문자·숫자, 혼동 문자 제외.
- 사용 문자 집합: ABCDEFGHJKLMNPQRSTUVWXYZ23456789.
- 코드는 방 생성 트랜잭션에서 유일성 보장. 중복 시 재생성.
- 코드가 재사용되지 않도록 보관 중 유일성 유지.
- 참여 URL: /join?code=XXXXXXXX. 강사 인증 비밀을 URL에 넣지 않는다.
- 초기 정원: 수강생 30개의 서로 다른 세션 + 강사 1명.
- 참여 이력 기준 정원. 연결이 끊겼다고 슬롯을 자동으로 재사용하지 않는다.
- 과제 파일럿은 서버의 생성 코드 검증을 통과한 사람만 방 생성. 일반 회원가입은 없음.
- 생성 코드는 서버 환경변수의 해시로 검증하며 프런트 코드에 포함하지 않는다.
- 접근 코드 요구는 강사의 방 생성에만 적용. 학생에게는 참여 코드만 필요하다.
- 공개 상용 서비스의 강사 인증·결제·조직 권한은 별도 설계 대상.

### ROOM-02 참여

- 코드 입력: 양끝 공백·중간 공백·하이픈 제거 후 대문자 변환. 이후 8자리와 문자 집합 검증.
- 유효하지 않은 코드와 없는 방: “참여 코드를 다시 확인해주세요.”
- 종료 방: 신규 참여 거절, 기존 멤버만 읽기 가능.
- 정원 초과: “참여 인원이 가득 찼어요.”
- 동일 인증 세션의 재참여는 기존 멤버를 반환하고 인원 증가 없음.
- 닉네임·이름·이메일 입력을 요구하지 않는다.
- 같은 브라우저 프로필의 여러 탭은 같은 사용자로 취급한다.
- 다른 기기·시크릿 모드·사이트 데이터 삭제는 다른 세션이다. 사람 단위 중복을 보장하지 않는다.
- 강사는 자신의 방에 학생으로 중복 참여할 수 없다. 테스트는 다른 브라우저 프로필 사용.

### ROOM-03 방 수명

- 생성 후 최대 12시간 open. 서버 UTC 시각으로 자동 마감 시각 설정.
- 강사가 조기 종료 가능. 종료 확인 문구: “방을 종료하면 새 응답과 질문을 받을 수 없어요. 종료할까요?”
- 종료 시 활성 요청을 같은 트랜잭션에서 종료.
- 종료 후 24시간 동안 기존 멤버에게 읽기 제공.
- 24시간 경과 시 접근 차단. 1시간 주기 삭제 작업으로 늦어도 종료 25시간 후 앱 DB의 방 관련 데이터 삭제.
- 생성 후 방치되어도 created_at+12h를 ended_at으로 사용.
- 자동 종료는 정기 작업과 모든 서버 요청 시 검사를 함께 사용해 만료 후 쓰기를 차단.
- 정기 작업 누락은 운영 오류로 알림·점검. 접근 차단만으로 삭제 완료라고 주장하지 않는다.

### ROOM-04 강사 복구

- 동일 브라우저 세션 새로고침: 소유권 유지.
- 강사 연결 끊김: 방과 요청은 유지, 학생에게 “강사 연결을 확인하고 있어요.”
- 강사가 사이트 데이터를 삭제하거나 다른 기기로 이동: v1 소유권 복구 없음.
- 초기 화면 안내: “이 브라우저의 사이트 데이터를 지우면 강사 권한을 복구할 수 없어요.”
- 공동 강사·권한 이전·복구 링크는 제외.

### 8.2 창 크기와 레이아웃

- 응답·진행 기본 요청 크기: 240×160 CSS px. (v1.1 사용자 결정, 기존 340×280)
- 사용자가 ‘더 작게’ 버튼을 누르면 200×120으로 축소, 다시 누르면 기본 크기로 복귀. 축소 상태에서는 집계 줄 등 보조 정보를 숨긴다. (v1.5) 강사 진행 중 집계는 축소 시 과반 안내 줄도 숨기고 숫자·막대만 둔다. 축소 시 한 줄에 안 들어가는 긴 학생 선택지(7자 초과, 예: ‘다시 설명해주세요’)는 짧은 말(‘다시 설명’)로 보여주고 전체 문구는 title·aria-label로 제공한다.
- (v1.5) 작은 창 상단 버튼: 크기 ‘−’(더 작게)/‘＋’(기본 크기로), ‘↗’ 원래 탭으로 돌아가기(사용자가 누를 때만, 작은 창은 닫지 않음). 모두 aria-label·title 필수.
- (v1.5) 학생 방 화면(원래 탭)은 입장 직후 “먼저 작은 창을 띄워주세요” 안내 상자와 ‘작은 창 띄우기’ 버튼을 맨 위에 둔다(자동 열기는 하지 않음, PIP-01). 원래 탭의 응답 화면은 ‘작은 창 없이 여기서 쓰기’를 눌러야 펼친다. 작은 창 미지원 브라우저·종료된 방에서는 바로 보여준다.
- 질문 탭으로 바꿔도 창 크기를 바꾸지 않는다 (v1.2). 근거: 웹은 PiP 창 위치를 지정할 수 없어, 화면 가장자리에서 창을 키우면 Chrome이 창을 안쪽으로 옮기고 다시 줄여도 원래 위치로 돌아가지 않음(GATE-01 2차). 기존 380×480 확장 폐기.
- 창 크기는 사용자의 ‘더 작게’ 버튼 클릭이나 직접 드래그로만 바뀐다. 자동 수신 이벤트로 크기 변경하지 않는다.
- 브라우저가 요청 크기를 조정할 수 있으므로 실제 크기에 반응형 대응.
- 최소 검수 콘텐츠 영역: 200×120. 이 크기에서 탭·요청 문구·응답 버튼 두 개가 잘리지 않아야 한다. 이보다 작은 사용자가 지정한 크기에서는 세로 스크롤을 허용.
- 가로 스크롤 금지, 버튼·문구 잘림 금지.
- OS 창 테두리·닫기·위치 이동은 브라우저가 담당. 위치 자동 지정·복원을 보장하지 않음.
- 1366×768 배율 125%에서 질문 창 하단 접근성을 확인.
- 초기 목업에서 브라우저 제목 표시줄을 없앨 수 있는 것처럼 표현하지 않는다.

### 8.3 공통 시각 규칙

- 배경 흰색, 본문 짙은 회색, 선택은 테두리·아이콘·문구를 함께 사용.
- 긍정·대기는 같은 크기. ‘대기’를 오류 색으로 표현하지 않는다.
- 본문 14px 이상, 주요 질문 16px 이상(작은 창 기본·축소 크기에서는 14px 허용, 한 줄 말줄임). 응답 버튼 클릭 영역 최소 44px 높이. 작은 창의 탭·크기 버튼은 최소 32×32px (v1.1).
- 작은 창 질문 탭 예외 (v1.2, 사용자 시험 후 결정): 질문 목록·입력 글씨 12px, 질문 한 줄 높이 28px, 🙋 버튼 34×28px, 남기기·정렬은 32×32px 아이콘 버튼(aria-label·title 필수).
- 작은 창의 스크롤 목록은 직접 구현한 스크롤 막대(폭 16px, 손잡이 최소 28px)를 사용한다. 근거: PiP 창에서 기본 스크롤바 드래그가 동작하지 않음(휠은 정상, 원인 미확정). 휠·키보드 스크롤은 유지.
- 상태는 색만으로 구분하지 않는다.
- 애니메이션: 선택 피드백 최대 150ms, 점멸·진동·자동 소리 없음. 예외(v1.4): 재촉 알림의 빨간 테두리 점멸(0.8초 주기 3회, prefers-reduced-motion이면 점멸 없이 테두리만)과 짧은 알림음(학생 설정으로 끌 수 있음).
- 탭 순서: 상단 탐색 → 본문 액션 → 하단 보조 액션.
- 키보드 포커스 표시, Tab/Enter/Space 사용 가능. 전역 단축키 없음.
- 상태 메시지는 aria-live polite. 새 질문으로 포커스를 이동시키지 않는다.

### 8.4 학생 응답 화면

상단: 수업명(한 줄 말줄임, 전체 제목 접근 가능) / 연결 상태.
탭: 응답 / 질문(N). N은 숨김 제외 미답변 질문 수이며 알림 읽음 수가 아니다.
본문: 현재 요청, 큰 버튼 두 개.
하단: “미응답” 또는 “전송 중…”. (v1.5) 서버 승인 후에는 하단 문장 대신 선택한 버튼이 진한 색 + 모서리 ✓로 바뀌고, “✓ 전송 완료”가 작은 창 아래쪽에 약 1.6초 떴다 사라진다(포커스·클릭을 가져가지 않음). 보내는 중 선택 예정 버튼은 연한 색 테두리로 구분한다. 화면 읽기 프로그램에는 “‘준비됐어요’로 전달했어요”를 aria-live로 알린다. 버튼 글자는 줄바꿈하지 않는다.
실시간 요청 없으면 “현재 응답 요청이 없어요. 실습을 계속해주세요.”
학생에게 전체 응답 비율·다른 학생의 선택·개별 이름을 제공하지 않는다.

### 8.5 강사 진행 화면

요청 없을 때: 준비 확인 / 이해 확인 / 진행 확인.
활성 요청 있을 때: 현재 질문, 긍정·대기·미응답 수, 대상 인원, 연결 미확인 수, 요청 종료.
다른 요청을 보내려면 기존 요청 종료를 먼저 해야 한다. 활성 요청 중 새 요청 버튼 비활성.
마지막 종료 요청 집계는 다음 요청 생성 전까지 ‘종료된 확인’ 표시와 함께 보여준다. (v1.5) 이때 연결 인원은 제목 줄 오른쪽 “연결 N명”으로 붙이고, 작은 창 집계 숫자는 13px, 확인 버튼 높이는 28px로 해 240×160 안에서 스크롤 없이 지난 결과와 다음 확인 버튼을 함께 보여준다.
질문 탭의 미답변 수는 대기 중에도 표시한다.
(v1.4) 집계는 대상 인원 대비 %와 50% 표시선 막대, 과반 안내 문구(예: “✓ 과반이 ‘준비됨’”, “‘준비됨’ 과반까지 3명”)를 함께 보여준다. 색만으로 구분하지 않는다.
(v1.4) 재촉하기: 진행 중인 확인에서 강사가 🔔를 누르면 그 확인의 미응답 대상자에게만 알림이 간다. 횟수 제한 없음(연타 방지만). 강사에게는 보낸 횟수만 보이고 누가 미응답인지는 보이지 않는다. 학생 작은 창은 빨간 테두리가 3번 깜빡인 뒤 응답할 때까지 유지되고, 상태 줄에 “강사님이 응답을 기다리고 있어요”, 질문 탭에 있으면 응답 탭에 빨간 점, 짧은 알림음(원래 탭에서 끄기 가능). 자동 탭 이동·크기 변경·포커스 이동은 하지 않는다.
(v1.4) 원래 탭에 지난 확인 기록(최근 20개, 집계만)을 보여준다. 학생은 요청이 없을 때 지난 확인에 대한 자기 응답만 본다.

### 8.6 질문 화면

학생 작은 창 질문 탭 (v1.2, GATE-01 목업 `src/gate/QuestionMock.tsx` 기준):

```
┌ 240×160 ─────────────────────┐
│ [응답][질문]       🙋⇅  ● ⤡  │  탭 줄: 정렬 아이콘(질문 탭에서만)
│ [익명 질문·찾기 (이름·키 X)][➤]│  입력칸 하나로 찾기 + 쓰기
│ useEffect 의존성 배열…   🙋4 ▐│  한 줄 요약, 🙋는 같은 줄 오른쪽
│ .env 파일은 깃허브에…    🙋5 ▐│  목록만 스크롤 (직접 만든 막대)
└──────────────────────────────┘
```

- 입력칸 하나로 찾기와 쓰기를 겸한다. placeholder: “익명 질문·찾기 (이름·키 X)”, 접근성 라벨에 개인정보·비밀정보 금지 안내 포함.
- trim 후 2글자 이상 입력하면 목록이 비슷한 질문만 남도록 즉시 좁혀진다. 상태 줄: “비슷한 질문 N · 같으면 🙋” 또는 “비슷한 질문 없음 · ➤로 남기기”와 글자 수 N/200. 입력 중에만 표시.
- 비슷한 질문 판정(클라이언트, 현재 불러온 목록 대상): 공백·문장부호를 뺀 두 글자 묶음 중 질문에 들어 있는 비율 ≥ 0.5, 또는 입력의 영어·숫자 단어(2자 이상)가 모두 질문에 부분 포함. 한글↔영어 표기 차이(깃↔git)는 v1 범위 밖. 사용자가 고르는 보조 표시이며 자동 병합·자동 차단이 아니다.
- 제출은 ➤ 아이콘 버튼만 사용. Enter는 줄바꿈.
- 질문 줄: 한 줄 말줄임. 누르면 최대 3줄까지 펼침, 3줄을 넘는 본문은 원래 탭 화면에서 전체 확인.
- 목록 기본: 미답변 / 🙋 많은 순 (v1.2 변경, 기존 최신순). 근거: 작은 창에서 중복 질문을 먼저 보게 함. 탭 줄 아이콘(🙋⇅ ↔ 🕒⇅)으로 최신순 전환.
- 필터: 미답변·답변 완료. 숨김 질문은 목록에서 제외.
- 정렬: 최신순(created_at DESC, id DESC), 공감순(count DESC, created_at ASC, id ASC).
- 카드(원래 탭·강사 화면): 질문 본문·서버 등록 시각 HH:mm·상태·🙋 저도 궁금해요 N. 작은 창 한 줄 보기에서 시각은 title로 제공.
- 작성자에게만 ‘내 질문’ 표시. 작성자 이름이나 공통 익명 번호 없음.
- 긴 URL·연속 문자열 줄바꿈. HTML은 문자열로 표시, 링크 자동 활성화 없음.
- 20개 단위 더 보기. 필터·정렬 변경 시 첫 페이지부터.
- 실시간 데이터 변경 시 보고 있는 목록 순서를 갑자기 바꾸지 않는다. 상단 ‘목록 업데이트’ 표시를 누르면 서버 기준 재정렬. 카드 상태·공감 수는 즉시 갱신.
- 숨겨진 카드는 즉시 제거. 현재 입력 초안과 스크롤은 최대한 유지.

### 8.7 강사 질문 처리

- 강사는 질문·공감을 직접 작성하지 않는다.
- 질문별 ‘답변 완료’ 클릭 → 서버 승인 후 완료 필터로 이동.
- 구두로 답변해도 완료 처리 가능. 답변 텍스트 입력은 제외.
- 실수 복구를 위해 완료 필터에서 ‘미답변으로 되돌리기’ 제공.
- 부적절하거나 개인정보가 포함된 질문은 ‘숨기기’ 가능. 확인 필요.
- 숨김은 v1 UI에서 복구 불가. 작성자 포함 일반 스냅샷에서 본문 제거.
- 답변 완료된 질문은 공감 신규·취소를 막고 최종 공감 수를 표시.
- 숨김·완료와 공감 변경이 경쟁하면 DB 잠금 획득 후 최신 상태로 판정.

## 9. PiP 동작 계약

### PIP-01 열기

- feature detection: documentPictureInPicture 존재 여부 확인.
- 자동 열기 금지. 사용자의 ‘작은 창 띄우기’ 클릭에서 requestWindow 호출.

### PIP-02 상태 공유

- 원래 탭의 인증·서비스 상태와 PiP 렌더링은 하나의 상태 저장소를 공유.

- PiP가 닫히면 일반 페이지에서 현재 서버 상태 표시. 수강생을 퇴장시키지 않는다.
- PiP 내부 클릭은 해당 창에 포커스를 줄 수 있다. 클릭 후 VS Code로 자동 포커스 이동시키지 않는다.

### PIP-03 닫기·새로고침

- 사용자가 작은 창을 닫으면 상태 감지 후 ‘다시 열기’ 제공.
- 원래 탭 닫기·새로고침 시 PiP 수명 변화는 브라우저에 따름. 유지 보장 없음.
- 재접속 시 서버 상태 복구 후 사용자 클릭으로 PiP 다시 열기.
- 작성 중 질문은 sessionStorage에 방별 저장하여 같은 탭 새로고침에서 복원.
- 초안은 서버에 전송하지 않고, 등록 성공·방 종료·명시적 방 나가기 시 삭제.
- 창을 닫았다는 이유로 방 종료 API를 호출하지 않는다.

### PIP-04 새 요청 중 질문 작성

- 응답 탭: 새 요청 화면 즉시 표시.
- 질문 탭: 현재 입력 유지, “새 응답 요청” 배지 표시. 자동 탭 이동·자동 크기 변경 없음.
- 사용자가 배지를 클릭하면 응답 탭으로 전환.
- 요청 종료 시 미전송 이전 응답을 새 요청에 적용하지 않음.

## 10. 실시간 상태 응답 명세

### RESP-01 고정 요청 사전

| type | 질문 | yes | no |
|---|---|---|---|
| ready | 실습할 준비가 됐나요? | 준비됐어요 | 잠시만요 |
| understood | 여기까지 이해됐나요? | 이해했어요 | 다시 설명해주세요 |
| proceed | 다음 단계로 넘어갈까요? | 좋아요 | 조금만 더요 |

문구는 서버·프런트 공통 enum 매핑으로 관리한다. 저장 값은 yes/no이며 화면에는 문맥에 맞는 문구를 사용한다. 강사 자유 질문은 제외.

### RESP-02 대상자와 분모

정확한 집계를 위해 요청 시작 시 대상자 목록을 고정한다.

- 시작 시점에 방에 참여했고 최근 45초 내 heartbeat가 확인된 학생만 대상.
- 강사 제외.
- 대상이 0명이면 요청 생성 거절: “연결된 수강생이 없어요.”
- 대상자는 round_targets에 서버가 저장한다.
- 요청 시작 후 입장한 학생: “이번 확인은 시작됐어요. 다음 확인부터 참여할 수 있어요.”
- 요청 도중 연결이 끊긴 대상자도 분모에서 제거하지 않는다.
- 연결 미확인 수는 별도 참고값이고 긍정·대기·미응답과 중첩될 수 있음.
- 해당 요청의 대상 학생만 응답 가능.
- 긍정 + 대기 + 미응답 = 요청 시작 시 대상 인원.
- 미응답 = 대상 인원 - 응답 행 수.
- 표시 예: “이번 확인 대상 25명 · 좋아요 18 · 조금만 더요 4 · 미응답 3 / 대상 중 연결 미확인 1”.
- 강사 현재 연결 인원과 회차 대상 인원을 구별하여 표시.

### RESP-03 생성·변경·종료

- 방당 활성 요청은 최대 1개. DB 제약으로 강제.
- 요청 생성 시 고유 round_id를 부여.
- 첫 응답은 insert, 변경은 동일 (round_id, member_id) 행 update.
- 같은 값 재클릭은 상태 변화 없음. 공감처럼 응답 취소하지 않는다.
- 변경 가능 시간은 요청이 open인 동안.
- 요청 종료 시 기존 선택과 집계 동결.
- 새 요청은 모든 대상자에게 미응답으로 시작.
- 종료 후 도착한 요청은 ROUND_CLOSED. 다음 회차로 이월 금지.
- 요청 종료와 응답이 경합하면 room → round 순서로 DB 잠금 후 처리. 먼저 확정된 트랜잭션 순서를 따른다.

### RESP-04 전송 UI

1. 클릭 시 선택 예정 표시와 ‘전송 중…’.
2. 승인 전에는 ‘전달했어요’ 표시하지 않음.
3. 1회 전송 중 버튼 비활성. 승인 후 변경 가능.
4. 8초 내 확인 없음: “전송을 확인하지 못했어요. 상태를 다시 확인해주세요.”
5. 타임아웃은 실패 확정이 아니다. 스냅샷 조회로 반영 여부 확인.
6. 반영됐으면 성공, 아니면 사용자 ‘다시 보내기’.
7. 오류·종료 시 이전 확정 선택으로 복원.
8. 재시도는 같은 client_action_id로 수행. 네트워크가 복구됐다고 오래된 클릭을 자동 재전송하지 않음.

## 11. 익명 질문·공감 명세

### Q-01 작성

- plain text, trim 후 Unicode code point 기준 1~200자.
- JavaScript와 DB에서 동일한 길이 규칙 사용. JS Array.from(value).length에 대응.
- 공백·개행만 있으면 금지. 이모지 복합 문자가 여러 code point일 수 있음을 길이 UI와 동일 적용.
- HTML 실행·Markdown 렌더링·첨부 파일·스크린샷 없음.
- 제출 중 중복 클릭 방지.
- 등록 성공 전 입력을 지우지 않음.
- 성공: 초안 삭제, 내 질문을 목록에서 확인할 경로 제공.
- 같은 client_action_id 재전송은 새 질문을 만들지 않음.
- 같은 텍스트라도 새 action이면 별도 질문. 자동 중복 판정 없음.
- 최소 작성 간격: 같은 학생·방 기준 10초.
- 학생당 방 전체 최대 20개, 방 전체 최대 300개(숨김 포함).
- 한도 초과 시 데이터는 유지하고 추가 작성만 차단.
- 학생 수정·삭제는 v1 제외. 개인정보는 강사에게 숨김 요청.
- 입력 안내는 방어 수단일 뿐 자동 비밀정보 탐지 기능이 있다고 표현하지 않는다.

### Q-02 익명의 의미

- 다른 학생과 강사에게 이름·이메일·작성자 세션 ID·IP를 공개하지 않음.
- 질문 표시용 응답에는 question_id, 본문, 상태, 시각, 공감 수, 내 질문 여부, 내 공감 여부만 제공.
- 서버 운영자는 부정 사용 방지와 권한 처리를 위한 익명 인증 ID 및 DB 연결 관계를 기술적으로 볼 수 있음.
- 따라서 ‘아무도 추적할 수 없는 완전 익명’이라고 안내하지 않는다.
- 클라이언트 Network 탭·실시간 메시지에 작성자 식별 정보가 노출되지 않는지 검수.
- 질문 내용 자체에 사용자가 이름을 쓰면 익명성이 훼손될 수 있으므로 안내.
- 다른 학생의 응답 목록·멤버 ID 목록은 강사에게도 내려주지 않는다. 강사에는 집계만 제공.

### Q-03 공감

- 아이콘 하나: 🙋, 텍스트: 저도 궁금해요.
- 질문 작성자 자신의 공감 금지. ‘내 질문’ 표시.
- 다른 학생은 질문당 한 번. 서버 unique(question_id, member_id).
- 클릭은 ‘toggle’ 명령 대신 setReaction(desired=true/false)로 전송.
- 중복 전송·재시도로 토글이 뒤집히지 않게 함.
- 서버 승인 이후 확정 수 표시. 전송 중 버튼 잠금.
- 질문 상태 pending·방 open에서만 변경 가능.
- 완료·숨김·종료 시 변경 불가.
- 공감 수는 reactions 실제 행 수. 클라이언트 숫자 더하기로 영구 집계하지 않음.

### Q-04 상태 전이

| 이전 | 동작 | 이후 | 가능 역할 |
|---|---|---|---|
| 없음 | 질문 등록 | pending | 학생 |
| pending | 답변 완료 | answered | 강사 |
| answered | 미답변으로 복구 | pending | 강사 |
| pending/answered | 숨기기 | hidden | 강사 |
| hidden | 복구 | 지원하지 않음 | 없음 |

답변 처리 시 answered_at 저장, 복구 시 null. 숨김 시 hidden_at 저장하고 원래 상태는 운영 로그에서만 확인. 숨김 데이터도 보관 만료 시 삭제한다.

## 12. 상태 모델과 예외 처리

### 12.1 주요 상태

| 객체 | 상태 | 의미 |
|---|---|---|
| 방 | open / ended | 참여·쓰기 가능 / 기존 멤버 읽기 전용 |
| 요청 | open / closed | 응답 가능 / 집계 동결 |
| 연결 UI | connecting / live / reconnecting / unavailable | 연결 시도 / 동기화 가능 / 복구 중 / 복구 실패 |
| 쓰기 UI | idle / sending / confirmed / unknown / rejected | 대기 / 전송 / 승인 / 결과 미확인 / 거절 |
| PiP | unsupported / closed / opening / open / failed | 기능 감지·열기 상태 |

expired는 조회 계층의 접근 차단 상태이며 별도 방 행을 유지하기 위한 상태가 아니다. 데이터를 삭제한 후 기존 클라이언트에는 ROOM_EXPIRED로 안내할 수 있도록 로컬 종료 시각을 사용하고, 서버에서 식별 불가능하면 ROOM_UNAVAILABLE로 처리한다.

### 12.2 연결

- 각 활성 서비스 인스턴스는 15초마다 서버 heartbeat 시도.
- last_seen_at은 클라이언트 시각이 아니라 서버 시각.
- 최근 45초 초과는 연결 미확인. 집중하지 않음·퇴장으로 단정 금지.
- PiP 하나와 원래 탭은 한 heartbeat/구독을 공유.
- 동일 프로필의 별도 서비스 탭은 같은 멤버이므로 인원 중복 없음. 구독·heartbeat가 중복될 수 있어 테스트에서는 하나의 탭만 권장.
- heartbeat 주기·백그라운드 타이머 지연은 G6에서 검증. 미충족 시 임계값을 실측에 맞춰 문서 수정.
- 실시간 연결 실패 시 1·2·4·8·15초 간격, 최대 15초 + 소량 지터로 재시도.
- 복구 중 쓰기 잠금. ‘재연결 중’ 표시.
- 정상화 순서: 인증 복원 → 구독 연결 → 최신 snapshot 조회 → revision 정합성 확인 → 쓰기 활성.
- 30초 넘게 복구되지 않으면 ‘다시 연결’ 버튼.
- 포커스 복귀·online 이벤트·PiP 재열기 시 snapshot 갱신.
- 정상 연결 상태에서도 30초 간격으로 revision을 재확인해 누락 이벤트 복구.

### 12.3 주요 예외 표

| 상황 | 표시·동작 |
|---|---|
| 초기 데이터 없음 | 로딩 상태, 8초 후 재시도 안내. 빈 목록과 구분 |
| 질문 0개 | “아직 질문이 없어요. 궁금한 점을 남겨보세요.” |
| 완료 질문 0개 | “답변 완료된 질문이 없어요.” |
| 수강생 0명 | 요청 버튼 비활성, 코드 공유 안내 |
| 인증 만료 | 세션 갱신 시도. 실패 시 재입장, 기존 권한 복구 여부 안내 |
| 동시 요청 생성 | 먼저 생성된 요청만 유효, 나머지 ACTIVE_ROUND_EXISTS |
| 종료된 회차 응답 | 저장 거절, 종료 안내 및 최신 화면 |
| 방 종료 중 질문 제출 | 서버 처리 순서에 따라 성공 또는 ROOM_ENDED. 성공 확인 없이 입력 삭제 금지 |
| 숨겨진 질문에 공감 | QUESTION_UNAVAILABLE, 목록 갱신 |
| 잘못된 방 접근 | 서버 권한 차단, 내용 미노출 |
| API 429 | 대기 시간·다시 시도 안내 |
| API 500 | “처리하지 못했어요. 잠시 후 다시 시도해주세요.” 요청 ID만 운영 로그 |
| 서버 시간 만료 | 마지막 데이터를 현재 상태인 것처럼 표시하지 않음. 동기화 시각 표시 |
| 다른 PiP 사용으로 창 닫힘 | 닫힘 감지, 원래 탭에서 재열기 안내. 원인 추측하지 않음 |

## 13. 권장 구현 구조 — v1 기준

### 13.1 선택

- Frontend: React + TypeScript + Vite.
- Backend: Supabase PostgreSQL, 익명 Auth, RPC, private Realtime Broadcast.
- 배포: HTTPS 정적 프런트 호스팅. 공급자는 배포 시 결정하고 README에 명시.
- 데이터가 진실의 원천. Realtime은 변경 사실 전달용.
- AI API 사용 없음.
- (v1.3 변경) create_room도 다른 계약 함수와 같은 인증 RPC로 구현한다. 파일럿 생성 코드는 bcrypt 해시로 private.app_secrets에만 저장하고(운영자가 SQL로 설정, migration·프런트에 없음), 함수 안에서 extensions.crypt로 비교한다. 사용자 ID는 auth.uid()로만 얻고 요청 본문의 사용자 ID는 사용하지 않는다. 근거: Edge Function 없이 같은 보안 수준을 얻고 배포 단위를 줄임 (decisions D-019).
- 라이브러리 실제 버전은 착수 시 lockfile로 고정. 이 문서는 미확인 미래 버전을 지정하지 않음.

이 선택은 구현 제안이다. 과제에서 DB 사용이 불가하면 기술 구조와 범위를 먼저 재설계한다. localStorage만으로 다중 컴퓨터 동기화를 구현했다고 주장하지 않는다.

### 13.2 로그인 화면 없이 권한 구분

사용자에게 회원가입을 요구하지 않지만, 내부적으로 익명 인증 세션을 발급한다. “로그인 UI 없음”과 “인증·권한 검사 없음”을 구분한다. 요청에서 전달한 role 또는 member_id를 신뢰하지 않고 서버가 auth.uid()와 멤버십으로 결정한다.

### 13.3 데이터 접근 구조

1. 브라우저는 공개 가능한 프로젝트 URL·publishable key만 사용.
2. 원본 데이터는 노출되지 않는 private schema에 저장.
3. 허용 RPC만 authenticated 세션에서 호출 가능.
4. 함수는 서버에서 멤버십·역할·상태를 검사하고 필요한 필드만 반환.
5. DB 변경 트랜잭션이 room revision을 증가시킨다.
6. 같은 트랜잭션에서 private 채널에 최소 변경 알림을 기록.
7. 클라이언트는 알림을 받으면 권한 검증 snapshot을 다시 조회.
8. 질문 본문·작성자 ID·개별 응답은 Broadcast payload에 넣지 않는다.

SECURITY DEFINER 함수를 사용할 경우 고정 search_path, 완전 수식 테이블명, 실행 권한 최소화, 입력 검증, auth.uid() 필수 확인. private 원본 테이블의 직접 select·write를 막는다. 프런트 숨김 처리만으로 익명성을 구현하지 않는다.

### 13.4 Realtime 권한

- 채널명: room:<room_uuid>.
- UUID를 아는 것만으로 구독할 수 없어야 한다.
- 해당 방의 멤버이면서 보관 접근 기간 내인 경우에만 receive 허용.
- 클라이언트의 임의 Broadcast 발신은 차단. 서버의 변경 알림만 신뢰.
- public access 비활성.
- 종료 후에도 읽기 기간에는 종료 이벤트·최종 상태 조회 가능.
- 권한은 구독 단계와 모든 snapshot/RPC 단계에서 각각 검사.
- 백엔드 privileged key는 서버 전용. 브라우저·저장소·PR·화면에 노출 금지.

## 14. 데이터 모델

모든 ID는 UUID, 시간은 timestamptz UTC. 화면 시각은 Asia/Seoul. null 허용은 아래 정의에 따른다.

| 테이블 | 주요 필드 | 제약 |
|---|---|---|
| rooms | id, title, join_code, host_auth_id, status, created_at, auto_end_at, ended_at(nullable), revision bigint default 0 | join_code unique, status enum, host당 열린 방 1개 |
| room_members | id, room_id, auth_user_id, role, joined_at, last_seen_at | unique(room_id, auth_user_id), 방당 host 1개 |
| rounds | id, room_id, type, status, opened_at, closed_at(nullable) | 방당 open 1개 partial unique |
| round_targets | round_id, member_id | composite PK, 같은 room의 student만 |
| responses | round_id, member_id, choice, version int, created_at, updated_at | composite PK, target FK, choice yes/no |
| questions | id, room_id, author_member_id, body, status, version int, created_at, answered_at(nullable), hidden_at(nullable) | body 1~200 code point, author room 일치 |
| question_reactions | question_id, member_id, created_at | composite PK, 방 일치, 자가 공감 금지 |
| action_receipts | auth_user_id, room_id(nullable), action_id, operation, request_hash, response_json, created_at | unique(auth_user_id, action_id) |
| pilot_access_limits | key_hash, window_start, count | 서버 전용 생성·참여 제한 카운터 |
| telemetry | room_id, pseudonymous_actor, event_name, round_id(nullable), duration_ms(nullable), result, created_at | 허용 이벤트·필드만, 본문·코드·token 제외 |

### 14.1 무결성

- 소속 방 일치는 RPC만이 아니라 가능한 composite FK·제약·트리거로 방어.
- join·정원 검사는 room 행 잠금 안에서 수행.
- 요청 생성은 room 잠금, 대상 snapshot, round insert가 한 트랜잭션.
- 응답은 room → round 잠금, 대상 확인, 버전 확인, upsert.
- 공감·질문 상태는 room → question 잠금.
- 잠금 순서를 모든 함수에서 동일하게 유지.
- 삭제는 방 하위 데이터 cascade. 삭제 작업은 auth 레코드 별도 정리까지 포함.
- heartbeat·telemetry·receipt 저장은 room content revision 증가를 유발하지 않는다.
- 실제 상태 변경 없는 동일 값 쓰기는 revision 증가 없음.
- 질문 숨김 시 방송에는 본문 없음, 이후 snapshot에서 숨김 내용 제외.

### 14.2 인덱스

room_members(room_id,last_seen_at), rounds(room_id,opened_at DESC), questions(room_id,status,created_at DESC), question_reactions(question_id), action_receipts(created_at), rooms(status,auto_end_at), rooms(ended_at).

## 15. 서버 함수 계약

### 15.1 공통 형식

쓰기 요청: action_id(UUID), 해당 객체 ID, operation별 payload, 필요 시 expected_version.
서버는 인증 사용자에서 역할을 유도한다. 클라이언트가 author_id·host_id를 지정할 수 없다.

성공:
```json
{
  "ok": true,
  "action_id": "uuid",
  "server_time": "2026-10-28T01:00:00Z",
  "room_revision": 12,
  "data": {}
}
```

실패:
```json
{
  "ok": false,
  "error": {
    "code": "ROUND_CLOSED",
    "retryable": false,
    "message_key": "round_closed"
  },
  "server_time": "2026-10-28T01:00:00Z"
}
```

JSON 예시는 계약 형식용 가상 값이다. 인증 오류·전송 계층 오류는 HTTP 상태와 앱 코드 둘 다 처리한다.

### 15.2 함수 목록

| 함수 | 요청 | 권한·검사 | 반환 핵심 |
|---|---|---|---|
| create_room | title, pilot_code, action_id | 익명 인증·생성 코드·열린 방 한도 | room_id, code, host snapshot |
| join_room | code, action_id | open·정원·중복 세션 | member role, room_id |
| heartbeat | room_id | 멤버·보관 기간 | server_time, room status |
| get_snapshot | room_id, question filter/sort/cursor | 멤버·보관 기간 | 역할별 snapshot |
| start_round | room_id, type, action_id | host·open·활성 없음·대상 >0 | round, target_count |
| set_response | round_id, choice, expected_version, action_id | 대상 학생·open | my_choice, version |
| close_round | round_id, action_id | host·방 open | 최종 집계 |
| create_question | room_id, body, action_id | student·open·길이·한도 | 질문 카드 |
| set_reaction | question_id, desired, action_id | 타인 질문·pending·open | reacted_by_me, count |
| set_question_status | question_id, desired_status, expected_version, action_id | host·open·전이 유효 | 상태, version |
| hide_question | question_id, expected_version, action_id | host·open | hidden 확인 |
| end_room | room_id, action_id | host | 종료 시각·최종 상태 |

### 15.3 충돌·멱등성

- action_id는 사용자의 새 의도마다 생성. 동일 의도의 재시도는 같은 값.
- 동일 action_id·동일 payload: 최초 확정 결과 반환.
- 동일 action_id·다른 payload: ACTION_ID_REUSED.
- receipt 확인·쓰기·상태 변경은 원자적으로 처리.
- 동시 최초 action 요청은 unique 충돌 처리 후 기존 결과 반환.
- 응답 최초 expected_version=0, 승인 시 1. 변경마다 +1.
- expected_version 불일치: VERSION_CONFLICT, 최신 상태를 조회하고 사용자에게 재선택 안내.
- question status도 같은 버전 규칙.
- 질문의 초기 version은 1이며 상태 변경·숨김마다 1 증가한다. 공감 변경은 질문 상태 version을 증가시키지 않는다.
- 공감은 desired 상태를 원자적으로 적용. 같은 상태 요청은 변화 없음.
- 여러 탭에서 다른 공감 의도가 동시 도착하면 서버 트랜잭션 처리 순서가 최종 상태.
- end_room과 close_round의 이미 완료된 동일 의도는 성공으로 반환.
- action_receipts는 방 보관 기간까지 유지, 생성 관련 orphan receipt는 48시간 후 삭제.

### 15.4 snapshot의 필수 필드

공통: room{id,title,status,ended_at,revision}, my_role, connection 확인 시각, active_round, latest_closed_round, pending_question_count, questions_page, next_cursor, server_time.

학생:
- active_round{id,type,opened_at,is_target,my_choice,my_response_version}.
- 다른 사람의 선택, 멤버 목록, 집계 없음.
- 질문 카드에 is_mine, reacted_by_me 포함.

강사:
- active_round{id,type,opened_at,target_count,yes_count,no_count,unanswered_count,target_connection_unknown_count}.
- current_connected_students.
- 학생 식별 정보와 개별 응답 없음.

동일 snapshot은 하나의 일관된 DB 읽기에서 생성한다. 별도 쿼리의 시점 차이로 합계가 어긋나지 않도록 한다.

### 15.5 대표 오류 코드

UNAUTHENTICATED, FORBIDDEN, INVALID_INPUT, ROOM_UNAVAILABLE, ROOM_ENDED, ROOM_EXPIRED, ROOM_FULL, ACTIVE_ROOM_EXISTS, ACTIVE_ROUND_EXISTS, NO_CONNECTED_STUDENTS, ROUND_CLOSED, NOT_ROUND_TARGET, QUESTION_UNAVAILABLE, QUESTION_NOT_PENDING, SELF_REACTION_NOT_ALLOWED, RATE_LIMITED, QUESTION_LIMIT_REACHED, VERSION_CONFLICT, ACTION_ID_REUSED, INTERNAL_ERROR.

권한 없는 사용자에게 방 제목·작성자·존재 여부 등 추가 정보를 오류로 노출하지 않는다.

## 16. 이벤트와 동기화

### 16.1 서버 Broadcast 계약

```json
{
  "event": "room_changed",
  "payload": {
    "room_id": "uuid",
    "revision": 13,
    "kind": "response_changed",
    "server_time": "2026-10-28T01:00:00Z"
  }
}
```

kind: round_started, response_changed, round_closed, question_created, reaction_changed, question_status_changed, question_hidden, room_ended, membership_changed, round_nudged(v1.4).

payload에 question body, author_member_id, choice, 인증 정보 없음. 클라이언트는 이벤트 값을 더해서 집계하지 않는다.

### 16.2 순서·누락

- revision <= 현재 revision: 중복·과거 알림 무시.
- 더 큰 revision 수신: 150ms debounce 후 snapshot 조회, 최대 지연 500ms.
- 받아온 snapshot revision이 현재보다 작으면 폐기.
- 구독 완료 후 snapshot을 읽어 구독 전후 틈의 누락을 복구.
- snapshot 로드 중 더 큰 revision을 받으면 재조회.
- 30초 주기 확인은 실시간 수신을 대체하는 주 통신 수단이 아니라 보완책.
- 방 종료는 다른 UI보다 우선 적용, 미전송 쓰기 잠금, 초안 삭제.
- connection heartbeat는 방송하지 않으며 강사 snapshot 조회 시 계산.
- 이벤트 유실·중복·순서 뒤바뀜을 테스트에서 주입한다.

## 17. 보안·개인정보·운영 제한

### 17.1 최소 수집

수집: 익명 인증 ID, 방 멤버십, 요청별 선택, 질문 본문, 공감, 서버 처리 시각.
수집하지 않음: 이름·이메일·전화번호·젭 ID·화면 내용·키 입력 기록·음성·영상.
네트워크·인증 공급자의 운영 로그는 공급자 정책에 따름. 앱 DB 삭제를 공급자 백업·로그 즉시 삭제로 설명하지 않는다.

### 17.2 접근 제어

- 참여 코드는 방 접근 수단이므로 외부 공개 금지 안내.
- 다른 방 snapshot·RPC·Realtime 접근 차단.
- host 명령은 auth.uid()와 room 소유권으로 확인.
- 모든 원본 테이블 직접 접근 차단.
- 데이터베이스의 service_role key는 클라이언트에 절대 넣지 않음.
- 익명 인증 사용자라는 이유만으로 전체 방 접근 허용 금지.
- 프런트 정적 빌드 파일에서 파일럿 생성 코드·비밀키 검색 검사.

### 17.3 악용 방지 기본값

- 방 생성: 인증 세션당 시간당 3회, 열린 방 1개.
- 잘못된 참여 코드: 세션당 10분 10회.
- 질문: 10초 1회, 학생당 20개, 방당 300개.
- 응답·공감: 세션당 각각 초당 3회, 분당 60회.
- 고의 세션 재발급을 완전히 막지는 못함. 공개 출시 전 CAPTCHA·네트워크 단위 제한을 추가 검토.
- 파일럿 생성은 공유된 운영 코드가 있는 폐쇄 테스트로 제한.
- Supabase 익명 인증에도 서비스 제공자의 rate limit이 있으므로 교실 공용 네트워크에서 30명 입장을 검증한다.
- 서버가 429를 반환하면 Retry-After 또는 앱 retry_after_seconds를 UI에 반영.

### 17.4 데이터 삭제

- 종료 24시간 이후 조회 차단, 다음 시간별 작업으로 데이터 삭제.
- 질문·응답·공감·멤버십·telemetry·receipt cascade 정리.
- 어떤 방에도 연결되지 않고 마지막 사용 후 48시간 지난 익명 인증 계정은 서버 관리 작업으로 정리.
- 권한 있는 운영자만 삭제 작업 실행.
- 사용자 테스트용 통계는 참여 동의하에 개인 식별·질문 본문을 제외해 별도 결과 문서에 기록. 원본 서비스 데이터 영구 보관 금지.

## 19. 비용·인프라 계획

2026-10-28 공식 가격 확인 기준, Supabase Free는 월 0달러이며 Realtime 무료 범위로 동시 연결 200개와 월 200만 메시지가 안내되어 있다. 무료 프로젝트는 비활성 기간에 일시 중지될 수 있다. 가격·정책은 배포 전 다시 확인한다.

- 파일럿 목표: 무료 플랜 범위 운영. 무료를 영구 보장하지 않음.
- 정적 프런트도 선택한 호스팅의 무료 한도·정책 확인.
- AI·파일 업로드·영상 처리 없음.
- 메시지 비용은 클릭 수와 동일하지 않음. 수신자 수·이벤트 종류·heartbeat·snapshot 요청·DB 저장량을 각각 측정.
- 한 사람의 중복 탭은 실시간 연결 사용량을 늘릴 수 있음.
- 작은 창과 원래 탭이 구독을 중복 생성하지 않도록 구현.
- 매일 비용 대시보드 확인. 무료 할당량 70%를 운영 주의 기준으로 사용.
- 무료 한도 초과·프로젝트 중지 시 오류 안내와 수업의 기존 채팅 복귀 절차 제공.

- 발표 직전 서비스 활성 여부·키·DB·Realtime·배포 URL을 실제 기기에서 점검.

## 20. 사용자 테스트·평가 설계

### 20.1 최소 조사

강사 1명, 수강생 3~5명에게 실제 창 사용 흐름을 확인한다. 인터뷰 결과가 가설과 다르면 기능을 억지로 정당화하지 않는다. 질문 확인 담당자가 명확해야 테스트가 성립한다.

### 20.2 비교 조건

A: 현재 수업에서 사용하는 채팅 방식. 평소 이모지를 사용한다면 이모지를 허용한다. 비교를 유리하게 만들기 위해 A에 타이핑을 강제하지 않는다.
B: 본 서비스의 PiP 응답창.

조건별 동일 난이도의 VS Code 실습을 수행한다. A→B와 B→A 순서를 번갈아 배정한다. 같은 요청을 외워서 빨라지는 효과를 줄이기 위해 순서는 바꾸되 요청 수·종류는 맞춘다.

### 20.3 과업

- 준비·이해·진행 각 2회, 조건별 6회 응답.
- 한 회는 ‘대기’에서 ‘긍정’으로 변경.
- 익명 질문 한 건 작성, 다른 질문 공감·취소.
- 강사 역할 참가자는 20건의 질문 중 미답변 질문 5건을 찾아 처리.
- 참가자 5명이 두 조건을 수행하면 응답 관찰 60건. 참가자가 적으면 실제 표본 수대로 기록.
- 추가 안정성 시나리오 30건은 기능 시험이며 사용자 관찰과 구분.

### 20.4 기록 항목

참가자 익명 코드, 조건·순서, 과업 ID, 제시 시각, 응답 승인 시각, 성공 여부, 화면 전환 횟수, 오류 종류, 관찰 메모. 질문 본문·이름은 통계 기록에 포함하지 않는다.

### 20.5 계산

- 개인별 각 조건 응답 시간 중앙값을 산출.
- 개인 개선율 = (A 중앙값 - B 중앙값) / A 중앙값 × 100.
- 전체 요약은 개인 개선율의 중앙값과 범위.
- 15초 미응답은 성공 시간 표본에서만 제거하고, 별도 실패율 분모에는 포함.
- 조건별 미응답·실패 수 반드시 함께 보고.
- 미답변 식별은 정답 개수와 잘못 선택한 개수를 함께 기록.
- 표본이 작으므로 통계적 일반화·전체 학습 효과 개선을 주장하지 않음.
- 클릭 응답이 실제 이해도를 측정했다고 주장하지 않음.
- 정량 결과와 함께 ‘창이 가려서 방해됨’, ‘부정 응답이 부담됨’ 같은 관찰을 반영.

### 20.6 미달 시 해석

시간이 줄어도 미응답이 늘면 새 요청 인지 방식 문제를 검토한다. 응답은 빨라도 창이 실습을 가리면 크기·배치 선택을 조정한다. 강사가 질문을 확인하지 않으면 도구 문제와 운영 문제를 구분한다. 데이터가 불리해도 그대로 발표한다.

### 23.2 CLAUDE.md 필수 규칙

- PRD 요구 ID를 구현 변경에 연결한다.

- 응답 분모를 임의로 실시간 연결 인원으로 바꾸지 않는다.
- 미응답을 yes/no로 저장하지 않는다.
- 새 회차에 이전 응답 재사용 금지.
- 서버 승인 전 성공 표시 금지.
- private 원본 테이블 직접 노출 금지.
- PiP를 일반 팝업으로 교체하려면 PRD 변경 필요.
- 원래 탭·PiP의 중복 구독 금지.
- 테스트 결과·사용자 발언·수치 조작 금지.
- 새 기능 추가보다 P0 완주·검증 우선.
- 변경 후 관련 인수 테스트만 우선 실행하고 실패·미검증 범위를 기록.
